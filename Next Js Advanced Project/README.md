# Addis Eats — Day 45 Advanced Next.js Project

A small food-ordering app built on the existing Next.js App Router project. The work focuses on sessions, access checks, scoped data, live search, metadata and a verifiable performance workflow.

## Run locally

1. Install Node.js 20 or newer.
2. Copy `.env.example` to `.env.local` and set a unique `SESSION_SECRET` plus `NEXT_PUBLIC_SITE_URL=http://localhost:3000` for local testing.
3. Run `npm install`, then `npm run dev`.
4. Open `http://localhost:3000`.
5. Demo sign-in: use any email and password `addiseats-demo`.

The demo sign-in intentionally uses a shared exercise password. It is not production authentication; do not reuse it for real accounts. Production should use a real identity provider and persistent database.

## Routes and protection

| Route | Access | Check |
|---|---|---|
| `/` and `/menu` | Public | Indexable pages with route-specific metadata |
| `/orders` | Signed in | Middleware plus server-side signed-session check; query filters by the session user ID |
| `/checkout` | Signed in | Middleware plus server-side signed-session check; order action checks session again |
| `/sign-in` | Public | Server action validates demo credentials and sets a signed, HttpOnly, SameSite cookie |

`cancelOrder` checks the current session and compares ownership against the stored order before changing it. A caller-supplied order ID is never treated as proof of ownership.

## Live data

The menu page includes a search that waits 300 ms after typing before requesting `/api/dishes?q=...`. The endpoint returns filtered data and an update timestamp. The client refreshes the current query every 15 seconds and cancels updates after unmounting. Open DevTools → Network, type `doro` quickly, and verify that requests are debounced rather than sent for every keystroke; then wait to see the polling request.

## Performance evidence (complete on a real deployment)

Do not invent a score. Deploy a preview and record the actual numbers in `PERFORMANCE.md`:

1. Run `npm run build` and deploy the same commit to a preview URL.
2. Run Lighthouse in Chrome DevTools against the deployed home page and menu page, using mobile mode and the same conditions.
3. Save the before screenshot/report before changes and the after screenshot/report after changes. Compare Performance, LCP, CLS and transferred image/font bytes.
4. This project uses `next/font` with `display: swap`, responsive CSS, server-rendered menu content, and static/revalidated public routes. The hero uses a lightweight local SVG social card; it is not a substitute for measuring actual page images.

## Metadata and discovery

- Root Open Graph and Twitter card metadata use an absolute `metadataBase`.
- Home, menu, dish detail, sign-in, checkout and orders have route-specific metadata.
- `/sitemap.xml` is generated by `app/sitemap.js`; `/robots.txt` by `app/robots.js`.
- Home page includes Restaurant JSON-LD.
- `public/social-card.svg` is the preview image. Replace the example domain in `.env.local` with the deployed canonical URL before publishing.

## Important limits

Orders currently live in process memory so they disappear after a server restart and are not shared across multiple deployment instances. The session cookie is signed and HttpOnly, but the middleware only checks for cookie presence as an early gate; the server-side `getSession()` performs signature and expiry verification. The demo sign-in and in-memory data are for learning, not production. For a real deployment, connect a database, use a production auth provider, and set `SESSION_SECRET` to a strong random value.
